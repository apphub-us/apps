# Stage 5 — conversation → job actions (append note, create measurement)

Module: `core/src/jobs/jobConversationActions.js` (CommonJS). Tests: `core/test/stage5JobActions.test.js` (authored, not
executed by the author). No UI, server, build script, HTML or generated file is part of this delivery.

## 1. Purpose and boundary

One reviewed conversation action becomes one record in the **original** job history, after an explicit confirmation:

| Action | Written by | Result |
| --- | --- | --- |
| `note` | `jobCardStore.save(jobId, expectedRevisionId, fields, [])` | one new job-card revision in which only `notes` changed |
| `measurement` | `jobMeasurementStore.create(jobId, fields)`, under the exclusive lock `empire-code-voice-save-v1` | one initial revision in the original measurement journal. No voice-journal marker is created or read |

- No new database, store, index, record kind or schema version. Historical reads (`read`, `history`, `readHistorical`,
  `list`) are unchanged and return the new records like any other.
- The adapter never deletes, overwrites, corrects or rolls back a record. The stores' own single-database transactions
  are the only atomicity; there is no cross-database rollback.
- The action cannot choose a job. `job` is the saved `{ head, revision }` the user selected in the app, read from
  `jobCardStore.read()`. An action carries no job reference and no identifier; extra keys are refused.
- Nothing is generated by a model or by randomness. Every identity is SHA-256 derived (section 4).
- Nothing is permanent without the user: no write happens without `{ accepted: true, planId }` for the exact plan.

## 2. Input (closed, bounded)

```
{ sourceId:       'conv1_' + 32 lowercase hex,          // app-owned conversation identity
  sourceRevision: integer 0..100,                       // app-owned
  sourceSavedAt:  'YYYY-MM-DDTHH:MM:SS.mmmZ',           // app-owned, canonical UTC: when the REVIEWED proposal was durably saved
  sourceText:     string, non-blank, 1..3000,           // the original words (same limit as /api/assist `text`)
  job:            { head, revision },                   // exact jobCard.js head + current revision, coherent
  action:         { kind: 'note', text }                // text: non-blank, 1..4000
                | { kind: 'measurement', fields } }     // fields: exactly jobMeasurement.FIELDS
```

Rules:

- Plain objects with exactly these keys. Accessors, symbols, class instances, unknown keys and unknown action kinds are
  refused; a getter is never executed.
- Text may contain tab, line feed and carriage return; other C0 control characters are refused. Text is never trimmed,
  normalized or shortened. Over-long text is `LIMIT`, not a cut.
- `job` must satisfy `jobCard.readHead` / `readRevision` and agree with itself (job id, current revision id, revision
  number). Otherwise `JOB_REQUIRED`.
- `sourceSavedAt` is the record time (section 4). It must be the save time of the durably saved assistant proposal the
  user is reviewing, not the time the conversation started. If it is earlier than `job.revision.savedAt` the input is
  refused with `SOURCE_OUTDATED` (by `validate`, `prepare` and `commit`): a record is never dated before the job
  revision it is attached to, and the time is never adjusted here. After a manual job edit the host saves the proposal
  again (new `sourceSavedAt`) and only then calls `prepare`. Equal times are accepted.
- `measurement.fields` is validated only by `jobMeasurement.validateFields`: the ten canonical fields
  (`label, quantity, valueText, unit, location, measuredLocal, utcOffset, mode, instrument, notes`), a listed
  quantity/unit pair, a plain finite decimal `valueText`, an explicit local time and UTC offset. No unit, value, mode or
  observed time is inferred, converted or defaulted. A failure is `VALIDATION` with the model's own messages.

## 3. API

```
validate(input)                                  -> { ok: true, input } | refusal          sync, pure
prepare(input, { crypto })                       -> { ok: true, plan, review } | refusal   async, deterministic, no storage
validatePlan(plan)                               -> { ok: true, plan } | refusal           sync, pure
pendingReceipt(plan)                             -> { ok: true, receipt } | refusal        sync, pure
validateReceipt(receipt)                         -> { ok: true, receipt } | refusal        sync, pure
commit(plan, currentInput, confirmation, opts)   -> result (section 6)                     async, the only writer
reconcile(receipt, { crypto, indexedDB })        -> result (section 6)                     async, read-only
```

Constants: `PLAN_KIND`, `RECEIPT_KIND`, `VERSION` (1), `LIMITS` (`sourceText` 3000, `noteText` 4000, `sourceRevision`
100, `jobNotes` = `jobCard.LIMITS.notes`), `NOTE_SEPARATOR` (`"\n\n"`), `STATUS`, `RECEIPT_STATES`.

`prepare` is asynchronous only because SHA-256 comes from `crypto.subtle.digest`. It uses no clock, randomness or
storage; the same input always gives the identical plan. The input is copied synchronously before the first `await`.
Without Web Crypto the result is `UNAVAILABLE`; there is no fallback identity.

`commit` options: `{ crypto, indexedDB, locks, persistPending }`. `locks` (the Web Locks manager) is required for a
measurement: its search, job check and write run under the exclusive lock `empire-code-voice-save-v1`, the same lock
the original capture journal holds while it creates measurements. A note takes no lock. `persistPending` is
**required for every new write** (note and measurement): an async function that resolves exactly `true` once the
pending receipt is durably stored (section 7). Options are not key-checked, so a missing, `undefined`, misspelled or
non-function hook is treated exactly like a hook that failed: `PENDING_MARKER`, `stored: false`, nothing written. Only
the read-only answer for a record that is already stored (`confirmed`, `reconciled: true`) does not need the hook.

No function throws on bad input. A refusal is `{ ok: false, status: 'refused', code, problems: [string] }`.

## 4. Plan and identities

```
{ kind: 'empire-code.job-action-plan', version: 1,
  id: 'jact1_' + 32 hex,
  action: 'note' | 'measurement',
  binding: { inputHash, sourceFingerprint, sourceId, sourceRevision, sourceSavedAt },
  job:     { jobId, jobRevisionId, revisionNumber },            // the exact reviewed job revision
  record:  // note
           { revisionId: 'jrev1_…', parentRevisionId, revisionNumber, savedAt, recordHash, text, separator }
           // measurement
           { measurementId: 'meas1_…', revisionId: 'mrev1_…', savedAt, measuredAt, recordHash, fields } }
```

All hashes are SHA-256 over canonical JSON (sorted keys, no whitespace) of a domain-tagged array; identifiers use the
first 32 hex characters.

| Value | Hashed content |
| --- | --- |
| `sourceFingerprint` | `['ec-job-action-source-v1', sourceId, sourceRevision, sourceSavedAt, sourceText]` |
| `inputHash` | `['ec-job-action-binding-v1', <whole validated input>]` |
| plan `id` | `['ec-job-action-plan-v1', inputHash]` |
| note `revisionId` | `['ec-job-action-note-revision-v1', sourceId, sourceRevision, jobId, text]` |
| `measurementId` | `['ec-job-action-measurement-v1', sourceId, sourceRevision, jobId, fields]` |
| measurement `revisionId` | `['ec-job-action-measurement-revision-v1', sourceId, sourceRevision, jobId, fields]` |
| `recordHash` | the complete expected original record |

Consequences:

- The plan identity covers everything reviewed (source, source text, job head and revision, action). Any change gives a
  different plan.
- The record identity covers source + source revision + job + content only. The same action reviewed again against a
  later job head keeps its record identity, so it cannot be stored twice in one job.
- Two identical actions in the same source revision for the same job are one record. A new source revision is a new
  action.
- Record time is `sourceSavedAt` (`savedAt` of the note revision; `createdAt` and `savedAt` of the measurement), as in
  the existing conversation handoff. It is supplied by the host, never read from a clock here, and it is part of the
  plan: a retry of the same plan always carries the same time, so a retry stays idempotent. A different
  `sourceSavedAt` is a different plan (`STALE` at `commit`), never a silent re-dating.
- A plan made from a source saved before the reviewed job revision does not exist (`SOURCE_OUTDATED`, section 2).

`review` (returned by `prepare`, for display, not for storage):

- note: `{ action, jobTitle, appendedText, separator, notesBefore, notesAfter, expectedRecord }`
- measurement: `{ action, jobTitle, fields, measuredAt, expectedRecord }`

`expectedRecord` is the exact original-model record that will be stored.

### Note semantics

`notesAfter = notesBefore + separator + text`, where `separator` is `''` for empty notes and `"\n\n"` otherwise. Existing
notes are an exact prefix. Title, address, service-result links and `createdAt` come unchanged from the reviewed
revision. If `notesAfter` would exceed `jobCard.LIMITS.notes` (20000) the result is `LIMIT` with the available count;
nothing is cut. Only the reviewed text is appended: no conversation, plan or revision identifier is written into notes.

Separator alignment: the server preview (`ec.assist.jobNoteAppend.append.separator`, `docs/assistant-api-contract.md`
§3.3) and this adapter use the same separator, `"\n\n"` for a job that already has notes and `''` otherwise, so the
previewed `resultingNotesLength` is the stored length for the notes length the client sent. The server preview is still
only a preview built from a length: `review.notesAfter` / `review.separator` returned by `prepare` from the saved job
remain the authoritative text to show for confirmation, and they are what is stored and what the limit counts.

### Measurement semantics

`record.fields` is the reviewed reading (the ten canonical fields, unchanged). The expected record is
`jobMeasurement.createInitial(fields, { measurementId, revisionId, jobId, jobRevisionId, savedAt: sourceSavedAt })` with
`jobRevisionId` of the reviewed job: exactly what `jobMeasurementStore.create` builds from the pinned identities and
time. One measurement is one row written by one transaction of the original store, so no multi-action capture journal
is involved: `jobVoiceBatch` is not required, `empire_code_voice_batches` is never opened, and no marker can be left
pending for the original Jobs screen to resume. `sourceText` is hashed into the plan but stored nowhere by this module
(the conversation itself stays in the host's bank).

## 5. Receipt (what the frontend persists)

```
{ kind: 'empire-code.job-action-receipt', version: 1,
  state: 'pending' | 'confirmed' | 'conflict',
  planId, action, sourceId, sourceRevision, sourceFingerprint, inputHash, jobId, jobRevisionId,
  record: { store: 'job-card' | 'measurement',
            id,                 // job id for a note, measurement id for a measurement
            revisionId, recordHash,
            journalPlanId } }   // always null (no journal exists); the key is kept so the closed shape is unchanged
```

The receipt holds identities and hashes only, no note text and no reading. It is enough for `reconcile`.

## 6. Results of `commit` and `reconcile`

| `status` | Shape | Meaning |
| --- | --- | --- |
| `confirmed` | `{ ok: true, status, reconciled, receipt }` | the exact reviewed record is in the original history. `reconciled: true` means it was found already stored and nothing was written now |
| `pending` | `{ ok: false, status, code, problems, stored, receipt }` | not confirmed. `stored: false` nothing is stored; `stored: null` the outcome is unknown (storage could not answer, or the acknowledgement was lost: code `INTERRUPTED`). `stored: true` is no longer produced: a stored exact record is `confirmed`. Keep the receipt; repeat `commit` with the same plan and input, or call `reconcile` |
| `conflict` | `{ ok: false, status, code: 'CONFLICT', problems, existing, receipt }` | the allocated identity holds a different record. Nothing was overwritten or appended. Never retried automatically |
| `refused` | `{ ok: false, status, code, problems[, stored: false] }` | this call wrote nothing. With `stored: false` the history was checked and the record is absent |

Refusal codes: `CONFIRMATION` (absent, malformed or mismatched confirmation, or an invalid plan), `DECLINED`
(`accepted: false`), `STALE` (source, action, plan or job changed since review), `INVALID`, `LIMIT`, `VALIDATION`,
`JOB_REQUIRED`, `JOB_UNAVAILABLE` (the saved job is missing or could not be read for the write), `UNAVAILABLE`
(crypto, storage or locks), `PENDING_MARKER` (the required `persistPending` hook is missing, is not a function, threw
or did not resolve exactly `true`; always with `stored: false`), `COLLISION`, `SOURCE_OUTDATED` (section 2), and original store codes passed through (`CORRUPT`,
`UNSUPPORTED`). `reconcile` uses `pending` + `NOT_STORED` for "not in the history".

### `commit` order

1. Confirmation gate. `confirmation` must be exactly `{ accepted: true, planId }` with `planId === plan.id` and a
   plan of valid shape. Otherwise nothing is hashed, opened, locked, read or written.
2. `currentInput` is validated and prepared again; the result must equal the plan exactly, else `STALE`.
3. Read-only search for the exact planned record (`readHistorical(jobId, revisionId)` for a note,
   `measurementStore.read(jobId, measurementId)` for a measurement), compared by `recordHash` over every stored field.
   Found → `confirmed` without a write, whatever the job head is now. Different data → `conflict`. For a measurement
   steps 3–7 run under the exclusive lock, so a second confirmation of the same plan only finds the stored record.
4. Not stored: `jobCardStore.read(jobId)` must equal the reviewed `{ head, revision }` exactly, else `STALE`
   (`JOB_UNAVAILABLE` when the job does not exist). The record search is repeated once before refusing.
5. Required `persistPending(receipt)` hook, called once with the pending receipt. Anything other than a function that
   resolves exactly `true` (no key, `undefined`, a misspelled key, a non-function, a throw, `false`, any other value)
   ends the call with `PENDING_MARKER` and `stored: false`. No new write is ever attempted without it. Steps 3 and 4
   are read-only, so a record that is already stored is still answered `confirmed` without calling the hook.
6. One write:
   - note: a `jobCardStore` created with a one-shot source of the allocated revision id and `now = sourceSavedAt`;
     `save(jobId, reviewedRevisionId, { title, address, notes: notesAfter }, [])`. The store's expected-revision guard
     runs inside its own transaction. The returned revision must equal `expectedRecord`.
   - measurement: a `jobMeasurementStore` created with a one-shot source of the allocated measurement and revision
     ids, `now = sourceSavedAt` and a `readJob` that accepts only the exact reviewed `{ head, revision }`;
     `create(jobId, fields)`. The store validates the fields again, runs its job check immediately before its
     transaction, and adds the one row inside that transaction together with its limit and identity-uniqueness checks.
     The returned revision must equal `expectedRecord`. If the job changed after step 4, the store's own check refuses
     before anything is written: the result is `STALE` with `stored: false`, and nothing is left behind anywhere.
7. After any failed write the history is read again before the result is classified: stored → `confirmed`
   (`reconciled: true`); unreadable → `pending, stored: null` (never classified further); different → `conflict`; absent →
   `STALE` for a job conflict, the store's code for a definitive refusal, otherwise `pending, stored: false`.

A second identity for the same plan is never drawn: the pinned source refuses a second request, which is reported as
`conflict`.

### `reconcile`

Read-only. It never writes a record and takes no input, plan or confirmation. It opens the original stores the same way
their own reads do (an absent database is created empty by the original store on first open). Use it after a reload, a
lost acknowledgement or an import, before deciding anything about a pending receipt.

## 7. Host protocol

1. Build the input from app state: the saved conversation identity and the job returned by `jobCardStore.read()`.
2. `prepare` → show `review` → the user confirms or cancels. Cancel means no call, or `accepted: false`.
3. **Before `commit`**, durably store `{ plan, input, receipt: pendingReceipt(plan).receipt }` and stop edits of the
   source while it is pending. The code enforces this through the required `persistPending` option: an async function
   called once with the pending receipt immediately before the first write. It must resolve exactly `true` only when
   that marker is durable; otherwise (including a missing or misspelled option) the result is `PENDING_MARKER` with
   `stored: false` and nothing is written. It is not called when the record is already stored. The adapter cannot
   verify that the host's `true` is truthful; it only refuses to write without it.
4. `commit(plan, input, { accepted: true, planId: plan.id }, options)` and persist the returned receipt:
   - `confirmed` → replace the pending marker with the confirmed receipt;
   - `pending` → keep the marker; retry later with the same stored `plan` and `input`;
   - `conflict` → keep and show; do not retry;
   - `refused` → drop the marker only if `stored: false` is present, or after `reconcile` reported `NOT_STORED`.
   - A `NOT_STORED` answer is valid only for the read that produced it: the host must read again immediately before it
     drops a marker, and must discard an earlier `NOT_STORED` before any new commit.
5. After a reload: for every pending receipt call `reconcile`. `confirmed` → mark done. `NOT_STORED` → the user must
   review again (a new `prepare` from current state); the old plan is used only if its stored `input` is still exactly
   the current source and job. A source that fails `validate` cannot be saved.
6. Re-review after `STALE` or `SOURCE_OUTDATED`: first get a definitive answer for the old receipt (a refusal carrying
   `stored: false`, or `reconcile` → `NOT_STORED`) and drop it; read the job again; durably save the proposal again so
   that `sourceSavedAt` is its new save time; then `prepare` → review → confirm. If the host keeps `sourceRevision`
   for the re-saved proposal the record identity is kept (the action can still exist only once in the job); a new
   `sourceRevision` is a new action by definition. A `conflict` on a re-review means the identity already holds a
   record, normally the same action stored by an earlier review: reconcile the earlier receipt instead of retrying.

Idempotency does not depend on memory or on the marker: the same plan always targets the same record identity, and the
stored record is searched for before every write. The marker exists so that the user is told the truth after a reload.

## 8. Known limits

- Simulated evidence only: the tests use the existing IndexedDB test double. Native durability and cross-tab behavior are
  not established here.
- Removed limit: a measurement no longer goes through `jobVoiceBatch`, so the earlier dead end (a voice-journal marker
  left pending for a plan that could no longer complete, and the 200-marker journal capacity) no longer exists.
- Jobs and measurements are separate databases (existing design); there is no cross-database transaction. The
  measurement store checks the job immediately before its own transaction. If the job is edited after that check and
  before that transaction commits, the reading is stored exactly as reviewed, attached to the reviewed revision, and
  the result is `confirmed`. This is the original store's behavior for every manual reading as well.
- The lock serializes this adapter and the original voice capture. The original manual measurement form does not take
  it; it draws random identities, so it cannot collide with a derived identity.
- The measurement limits of the original store apply unchanged (`LIMIT`, `stored: false`).
- A job card keeps at most 1000 revisions (original limit); a note beyond that is refused with `LIMIT`.
- `sourceSavedAt` is the record time and the host is trusted to supply the real save time of the reviewed proposal.
  The only check here is that it is not earlier than the reviewed job revision (`SOURCE_OUTDATED`); a device clock that
  was wrong when either time was taken is not detected. No review-time field was added to the API.
- A superseded plan (same action, earlier job revision) answers `conflict` once a later review of that action is
  stored. It writes nothing; the host should have dropped it at `STALE` + `stored: false`.
- `persistPending` proves only that the host answered `true` before the write. Whether the marker really is durable is
  the host's responsibility; a host that answers `true` without storing it loses the reload receipt, not idempotency
  (the record identity and the search before every write do not depend on the marker).

## 9. Build integration

Add `{ id: 'jobConversationActions', file: 'jobs/jobConversationActions.js' }` to `MODULES` in
`core/tools/build-calc.js`, after `jobVoiceBatch`. It requires `./jobCard.js`, `./jobCardStore.js`,
`./jobMeasurement.js` and `./jobMeasurementStore.js` (no longer `./jobVoiceBatch.js`), all earlier in the list; the existing shim
resolves these forms without an alias. In the bundle it is `window.EC.jobConversationActions`.
