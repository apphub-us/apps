# LC-JOB-RESTORE-1 — guarded editable job recovery from `.ecjob`

## Scope

After opening a fully verified local `.ecjob` v1 in **Job archive files**, choose **Restore job — live browser**, read the warning, explicitly check the confirmation checkbox and press **Restore job into this browser**. This moves the archived saved job, its complete metadata revision chain, all measurement/material/photo detail history, verified original raster Blobs, and exact readable saved-result raw texts to the CURRENT browser profile and origin. It does NOT replace the read-only archive viewer, change the calculator draft, run NEC/NYCEC sizing, add Favorites, migrate databases, change job result interpretation, upload files, synchronize, delete old records or publish.

**Restore is refused if any imported ID is already present** in any destination store or saved-result localStorage. No replacement, revision merge, new-ID clone, or automatic renaming is supported. Reopening an archive of a job that still exists in Brave cannot restore a second copy into that same Brave origin; it is a duplicate by design. To test restoration from an existing job, use a separate EMPTY browser profile/origin. Do not clear or delete a live job to bypass this safeguard. An archive with unreadable, missing or inconsistent linked results remains browsable read-only but is refused for editable restoration: the app cannot claim to have restored complete data. No password or cryptographic authenticity is inferred from a checksum.

## Non-atomic stores and interruption recovery

The legacy system uses *four distinct IndexedDB databases* (jobs, measurements, materials and photos) plus *localStorage* (saved results). These cannot be covered by one native transaction. The restore algorithm makes an explicit durable operation marker in a new separate `empire_code_restore_operations` version-1 database after verifying archive bytes and checking destination keys. It writes saved results and independent journals first, each using native atomic IndexedDB transactions with **add()**, and writes the job head and full job revision chain **last**, in one final native transaction. Existing entries are never overwritten. It marks the journal as committed only after all targeted writes succeed. Success is reported only after successful commits. The journal marker is cleared when possible; a committed marker left by a cleanup failure can be cleared later.

On an ordinary in-process error the algorithm attempts *compensating rollback*: for each staged job/measurement/material/photo row it verifies that the resident record matches the exact archived version, checks photo bytes against their SHA-256 descriptor, and removes only matching staged entries. For each raw saved result it removes the key only if the current text still matches the value recorded in the restore journal. Nothing else is eligible for deletion. If a staged item has changed, rollback **refuses to delete it** and reports RECOVERY_REQUIRED. Unexpected shutdown, quota loss and blocked transactions can leave an operation marker and staged child records. The user must reopen the app and click **Check / recover interrupted restore** before trying another restore. Recovery and restore both require an exclusive browser Web Lock. Never claim cross-database crash atomicity or automatic rollback following sudden power loss; persistent uncommitted work remains a visible, recoverable state rather than being silently treated as a successful/empty job.

A restored job is exposed in the regular Job Cards list only after its final head transaction. Existing history, saved results and unrelated jobs stay untouched on failure. No automatic recovery is performed during ordinary app load; the explicit recovery button is a deliberate user action. Recovery without the Web Locks API is refused rather than doing unsafe multi-tab writes.

## Data and trust model

Use `src/jobs/jobArchiveFile.js.decode` for original archive bytes, canonical UTF-8 manifest validation and original-photo SHA checks; use `src/jobs/jobRestore.js` for exact-ID closed plan. `src/jobs/jobRestoreStore.js` alone performs bounded native writes and recovery. Its photo assets are the exact original raster Blobs reconstituted from the archive, with already validated descriptors. All preexisting src calculators, job/card stores, photo stores, archive encoders/decoders and schema versions are untouched. Existing UUIDs, saved revisions, producer fingerprints, historical timestamps and exact raw calculation texts stay unchanged. No recalculation, fallback, migration, field normalization, alias resolution or heuristic correction is permitted.

A new `empire_code_restore_operations` database tracks pending operations keyed by original jobId. It stores the proposed immutable row descriptors and exact saved-result strings so cleanup needs no reselected file; it does NOT duplicate original photo bytes. It is not a full backup and can be cleared only after an uncommitted restore is rolled back or a committed restore is confirmed. Photo metadata, image bytes and other browser data remain subject to browser quota and user storage deletion. No encryption or cloud backup is provided.

## Acceptance and delivery

The source package includes source-contract/adapter tests and a dependency-free native Chrome test script. Full developer verification checks the deterministic generated block and legacy calculator tests. The native acceptance MUST run on the user's Mac in a dedicated new Chrome profile and loopback-only server, with synthetic data; existing Safari/Brave profiles and localStorage are neither opened nor modified by the runner. It tests actual file selection, successful restoration, same-ID refusal, a mid-write injected rollback, explicit recovery and absence of calculation edits. The Mac installer MUST refuse to apply to the active test source unless the source pin matches the exact 201-file baseline, the full suite passes, the real Chrome test passes and the source remains unchanged during verification. The installer touches only the named test copy; never `EmpireCodeRepo` or user browser data. Safari, Brave and physical iPhone acceptance are separate from isolated Chrome tests.

## Limitations

Only **a new job with previously unused archive IDs** can be restored; an existing job cannot be replaced, merged or cloned in this version. All linked saved results must be readable and consistent. Recovery depends on data still being available in the browser and on successful writes after a storage failure; deliberate modification of staged records blocks automatic cleanup. Offline browser policies/storage restrictions may refuse restoration. The design is recoverable, not an ACID transaction across all browser storage engines. Preserve the downloaded `.ecjob` until successful live recovery is verified and do not delete it merely because a prepared archive appears onscreen.
