# LC-JOB-MATERIALS-1 — manual material list

Open a saved current Job card → Materials → Add material. Enter a name, positive quantity and explicit unit. Optional fields are multi-line specification/part number, multi-line location, supplier and notes. Status begins as Not recorded. Available manual statuses are Needed / to buy, Ordered, On site, Used (recorded) and Not needed. They do not place orders, deduct stock, verify purchase or approve electrical work.

Status applies to the entire row. Split partial batches into separate items; this slice does not track ordered/delivered/used subquantities. Identical names are not merged. Not needed preserves the row and all previous versions rather than deleting it. There is no purchase integration, stock ledger, automatic BOM, price/tax/total cost, unit conversion, import/export, cloud sync, photos or approval.

Quantity is retained as bounded decimal text, preserving trailing zeros and whitespace. Use a decimal point, no signs, comma, thousands separators or scientific notation. Zero is refused; use Not needed for a row that is no longer required. Count units pcs/box/pack/roll/set must be whole numbers (2.00 is accepted); length units ft/in/m/cm/mm may be fractional. The original unit is retained even when another field is edited.

Update item creates a new immutable version and requires a reason for a real change, including status changes. A new separate item is created with Add material. Unchanged Save writes nothing; stale writers still conflict first. View item history is read-only. Save/Discard are explicit; drafts can be lost on page reload and are not backups. Material, measurement and job editors cannot silently replace each other's drafts. Delayed navigation/reads are guarded; opening a new draft invalidates pending job navigation. History does not backfill later materials into older job metadata snapshots.

Pure model src/jobs/jobMaterial.js; native adapter src/jobs/jobMaterialStore.js. API validateFields, createInitial, createUpdate, readRevision, assemble and createMaterialStore(indexedDB,{crypto,readJob,now?}) → create(jobId,fields), update(jobId,materialId,expectedRevisionId,fields,reason), list(jobId), read(jobId,materialId), close(). Data: closed revision shape with kind, recordVersion, materialId, revisionId, parentRevisionId, revisionNumber, jobId, jobRevisionId, createdAt, savedAt, producer, item, changeReason. Fields are label/specification/quantityText/unit/status/location/supplier/notes. No electrical-calculator dependency.

New separate IndexedDB database empire_code_materials v1 uses an add-only revisions store, keyPath revisionId, indexes byJobId and byMaterialId. Current versions are derived from complete validated chains, never mutable heads. Secure 128-bit random IDs mat1_/trev1_ have bounded collision retries. Required job is verified by the unchanged job reader before writing. This is not an atomic transaction across the separate job/material databases; no placeholder job is made. Saving a material does not create a job metadata revision or change measurements/Favorites/full results.

Reads and writes report success only on transaction complete. Expected-revision comparison, chain validation, limit checks and row add occur inside the same readwrite transaction. Two tabs cannot overwrite the same version. An abort after a successful add still rolls back the change. Unsupported versions/schema, missing job, malformed chains, non-indexable entries, blocked/closed opens, quota and limits produce explicit refusal without repair or deletion. Input objects are independently copied before async calls.

Implementation limits: 500 items/job, 50 versions/item, 2000 revision rows/job, 50000 rows globally; these are not electrical or inventory limits. Unknown versions, unsafe non-JSON objects, accessors, cyclic/oversized data, invalid timestamps and ID mismatches are refused. Name/supplier are single-line; specification/location/notes/reason use textareas with original line breaks preserved.

All old source modules and schemas are preserved byte-for-byte. New modules are appended after the existing 25 bundle entries; three old test files change only their explicit module registry assertions. New styles are scoped to #lcContent. Ordinary UI uses text nodes and labelled 16px controls/44px buttons. Pure/simulated tests do not claim native browser evidence; completed Chrome scenarios and integrity reports live in the separate coordinator checkpoint. Safari/physical-iPhone/PWA acceptance is distinct.

Primary references: https://www.w3.org/TR/IndexedDB/ (completion/abort and transaction scheduling); https://html.spec.whatwg.org/multipage/input.html (single-line normalization). Application results must be established by executed tests, not inferred from these specifications.
